# ADR-017 — Api servida no mesmo site dos apps, sob /api

Status: proposta (arquiteto: Eric) · Baseline: 2026-11-03.1 · Requisitos: RF-01, RF-13, RNF-05

## Contexto
A ADR-004 guarda a sessão no cookie `sid` com `HttpOnly` e `SameSite=Lax` (RNF-05). O plano de operação (fase 8) põe os apps em hospedagem estática e a Api em outro serviço. Em domínios diferentes, o navegador não envia cookie `SameSite=Lax` em `fetch` de outro site: o login funcionaria e todas as rotas seguintes do editor dariam 401 (RF-01). Trocar para `SameSite=None` exigiria CORS com credenciais e abriria espaço para CSRF.

## Decisão
- Editor e Player chamam a Api sempre pelo caminho relativo `/api` (`PREFIXO_PUBLICO` em `apps/api/contrato`), no mesmo site em que foram servidos.
- Desenvolvimento: o `vite.config.ts` de cada app encaminha `/api` para a Api local (`http://localhost:3000`), removendo o prefixo.
- Produção (fase 8): a hospedagem dos apps reescreve `/api/*` para o serviço da Api (rewrite do Vercel/Netlify/Cloudflare ou proxy reverso no Docker Compose). Requisito de implantação, registrado para o responsável pela fase 8.
- As rotas no contrato `api.md` não mudam: o prefixo é retirado antes de chegar ao Fastify. Sem CORS.

## Consequências
- O cookie da sessão continua `SameSite=Lax`, primário e fora do alcance do JavaScript (RNF-05).
- O Player público (RF-13) não precisa de cookie, mas usa o mesmo caminho, e a configuração é uma só.
- Hospedagem que não permita reescrita de caminho não serve para os apps.
